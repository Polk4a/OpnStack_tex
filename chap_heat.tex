\section{Heat : l'orchestration}\label{chap:heat}
% =====================================================================

Heat décrit une infrastructure complète dans un fichier texte, puis la crée, la modifie et la détruit en appelant les API des
autres services. Ce chapitre présente son rôle, ses concepts (modèle, stack, ressource), son architecture, le format des
modèles, le cycle de vie d'une stack, les fonctions avancées (groupes, mise à l'échelle, composition) et la mise en œuvre.

% ---------------------------------------------------------------------
\subsection{Rôle et place de Heat}\label{sec:he-role}
% ---------------------------------------------------------------------

\begin{definition}{Heat}
Heat est le service d'orchestration d'OpenStack. Il lit un \gls{modeleheat} qui décrit des ressources et leurs liens, puis crée
une \gls{stack} qui les matérialise en appelant les API des autres services ; il offre pour cela une API REST native d'OpenStack
\parencite{heat-index}.
\end{definition}

\begin{itemize}
  \item \textbf{Problème.} Créer, reproduire et faire évoluer de façon fiable une infrastructure de dizaines de ressources
        liées (réseaux, serveurs, volumes) sans tout exécuter à la main (support de cours, chapitre 3, partie 3).
  \item \textbf{Communique avec.} Keystone (authentification et délégation de droits), puis les API de Nova (serveurs),
        Neutron (réseaux), Cinder (volumes) et des autres services dont les ressources figurent dans le modèle
        \parencite{heat-resource-types}. Heat orchestre les autres services ; il n'en remplace aucun.
  \item \textbf{Exemple.} créer une stack à partir d'un fichier :
\begin{lstlisting}[style=terminal]
$ openstack stack create -t mystack.yaml mystack
\end{lstlisting}
\end{itemize}

\begin{remarque}[Heat et Terraform]
Terraform décrit aussi une infrastructure par des fichiers, pour de nombreux fournisseurs. Heat est l'outil natif d'OpenStack :
intégré à Keystone et aux autres API, mais limité à ce périmètre (support de cours).
\end{remarque}

\subsection{Concepts : modèle, stack, ressource}\label{sec:he-concepts}

Plusieurs API peuvent tourner derrière un répartiteur HTTP ; plusieurs moteurs se partagent les messages de la file, qui les
distribue tour à tour \parencite{heat-scale}. Pour les opérations différées (la mise à l'échelle déclenchée plus tard, par
exemple), le moteur doit agir au nom de l'utilisateur sans disposer de son token. Il utilise donc un \gls{trust} créé à la création de la stack :
le propriétaire délègue au service Heat les rôles nécessaires, et le moteur obtient un token limité pour agir en son nom
\parencite{heat-auth-model}. Les utilisateurs que les modèles créent eux-mêmes vivent dans un domaine séparé, nommé \texttt{heat},
et ne portent que le rôle \texttt{heat\_\allowbreak stack\_\allowbreak user}, qui limite l'API accessible
\parencite{heat-stack-domain-users}.

% ---------------------------------------------------------------------
\subsection{Écrire un modèle HOT}\label{sec:he-modele}
% ---------------------------------------------------------------------

Un modèle HOT comporte une version (\texttt{heat\_\allowbreak template\_\allowbreak version}, obligatoire), une description, des
paramètres, des ressources (au moins une) et des sorties \parencite{heat-hello-world}. La version choisit les fonctions
disponibles et suit les versions d'OpenStack : \texttt{2013-05-23} pour Icehouse, \texttt{2018-08-31} pour Rocky,
\texttt{2021-04-16} pour Wallaby \parencite{heat-hot-spec}. Le modèle suivant crée un réseau, un serveur et un volume.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
heat_template_version: 2018-08-31
parameters:
  flavor: { type: string, default: m1.small }
resources:
  net: { type: OS::Neutron::Net }
  subnet:
    type: OS::Neutron::Subnet
    properties: { network: { get_resource: net }, cidr: 10.20.0.0/24 }
  server:
    type: OS::Nova::Server
    properties:
      image: ubuntu
      flavor: { get_param: flavor }
      networks: [ { subnet: { get_resource: subnet } } ]
  volume:
    type: OS::Cinder::Volume
    properties: { size: 10 }
  attach:
    type: OS::Cinder::VolumeAttachment
    properties:
      instance_uuid: { get_resource: server }
      volume_id: { get_resource: volume }
outputs:
  server_ip:
    value: { get_attr: [server, first_address] }
\end{lstlisting}
\end{minipage}\par

Un paramètre a un type (\texttt{string}, \texttt{number}, \texttt{json}, \texttt{comma\_\allowbreak delimited\_\allowbreak list},
\texttt{boolean}), une valeur par défaut (sans elle, l'utilisateur doit en fournir une), un attribut \texttt{hidden: true} qui
masque sa valeur (un mot de passe) et des contraintes (\texttt{allowed\_\allowbreak values}, \texttt{length}, \texttt{range},
\texttt{allowed\_\allowbreak pattern}) \parencite{heat-hello-world}. Les \emph{fonctions intrinsèques} du tableau~\ref{tab:he-fonctions}
relient les éléments entre eux ; \texttt{get\_resource} et \texttt{get\_attr} créent en même temps une dépendance
(section~\ref{sec:he-cycle}).

\begin{table}[!ht]
\centering
\renewcommand{\arraystretch}{1.3}
\begin{tabular}{@{}>{\raggedright\arraybackslash\ttfamily\small}p{3.0cm}>{\raggedright\arraybackslash}p{7.2cm}>{\raggedright\arraybackslash\ttfamily\small}p{5.3cm}@{}}
\toprule
\textrm{\textbf{Fonction}} & \textbf{Rôle} & \textrm{\textbf{Exemple}} \\
\midrule
get\_param & Valeur d'un paramètre. & \{ get\_param: flavor \} \\
get\_resource & Identifiant d'une autre ressource du modèle. & \{ get\_resource: net \} \\
get\_attr & Attribut d'une ressource, connu à l'exécution. & \{ get\_attr: [server, first\_address] \} \\
str\_replace & Remplace des chaînes dans un texte, par exemple un script de démarrage. & \{ str\_replace: \{ template: \dots, params: \dots \} \} \\
get\_file & Contenu d'un fichier, joint à la requête. & \{ get\_file: boot.sh \} \\
depends\_on & Dépendance explicite, sans référence (attribut d'une ressource). & depends\_on: server2 \\
\bottomrule
\end{tabular}
\caption{Fonctions intrinsèques et dépendances d'un modèle HOT \parencite{heat-hot-spec}.}
\label{tab:he-fonctions}
\end{table}

Un \gls{environnementheat}, passé avec \texttt{-e}, fournit des valeurs de paramètres (section \texttt{parameters}), des valeurs
par défaut pour tous les modèles imbriqués (\texttt{parameter\_\allowbreak defaults}) et des remplacements de types
(\texttt{resource\_\allowbreak registry}) ; ses valeurs l'emportent sur celles de l'opérateur du cloud \parencite{heat-environment}.

% ---------------------------------------------------------------------
\subsection{Cycle de vie d'une stack}\label{sec:he-cycle}
% ---------------------------------------------------------------------

Heat construit un \gls{graphedeps} à partir des références du modèle : une ressource qui référence une autre (ou l'un de
ses attributs), ou qui la nomme dans \texttt{depends\_on}, n'est créée qu'après elle \parencite{heat-glossary}. Les ressources
sans lien sont créées en parallèle \parencite{heat-environment}. La figure~\ref{fig:he-graph} montre le graphe du modèle
précédent ; la suppression suit l'ordre inverse.

Une mise à jour recalcule le graphe et ne touche que les ressources concernées. Pour chaque propriété modifiée, Heat met la
ressource à jour en place ou la remplace (il en crée une nouvelle, puis supprime l'ancienne). Pour un serveur Nova, par défaut,
changer le \texttt{flavor} le redimensionne, changer l'\texttt{image} le reconstruit, et changer le contenu de \texttt{user\_data}
le remplace \parencite{heat-resource-types,heat-software-deployment}. L'option \texttt{--dry-run} montre ces changements sans
les appliquer ; \texttt{--enable-rollback} (création) ou \texttt{--rollback} (mise à jour) demande un retour arrière en cas
d'échec \parencite{osc-stack}.

La mise à l'échelle combine un groupe, qui porte des bornes, et une politique. La politique expose une URL de signal : un appel
sur cette URL, par une alarme ou à la main (\texttt{openstack stack resource signal}), ajoute ou retire des serveurs. C'est une
opération différée, qui passe par le trust de la stack \parencite{heat-resource-types,heat-auth-model}.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
resources:
  group:
    type: OS::Heat::AutoScalingGroup
    properties:
      min_size: 1
      max_size: 3
      resource:
        type: server.yaml
  scale_up:
    type: OS::Heat::ScalingPolicy
    properties:
      adjustment_type: change_in_capacity
      auto_scaling_group_id: { get_resource: group }
      scaling_adjustment: 1
      cooldown: 60
outputs:
  scale_up_url:
    value: { get_attr: [scale_up, signal_url] }
\end{lstlisting}
\end{minipage}\par

D'autres services s'appuient sur Heat : Magnum génère une stack pour chaque cluster Kubernetes (chapitre~\ref{chap:magnum}).
Heat dispose aussi de types de ressources pour les répartiteurs Octavia (chapitre~\ref{chap:octavia}) et les conteneurs Swift
(chapitre~\ref{chap:swift}) \parencite{heat-resource-types}.

\subsection{Exercices corrigés}\label{sec:he-exercices}
% ---------------------------------------------------------------------

\begin{exercice}{Écrire un modèle}\label{ex:he-modele}
Écrire un modèle qui crée un réseau \texttt{app-net}, son sous-réseau \texttt{10.30.0.0/24} et un serveur \texttt{web}
d'image \texttt{ubuntu}. Le gabarit est un paramètre limité à \texttt{m1.small} ou \texttt{m1.medium} (par défaut
\texttt{m1.small}). Le modèle renvoie l'adresse du serveur. Comment créer la stack ?
\end{exercice}
\begin{correction}
\begin{lstlisting}
heat_template_version: 2018-08-31
parameters:
  flavor:
    type: string
    default: m1.small
    constraints: [ { allowed_values: [m1.small, m1.medium] } ]
resources:
  net:
    type: OS::Neutron::Net
    properties: { name: app-net }
  subnet:
    type: OS::Neutron::Subnet
    properties: { network: { get_resource: net }, cidr: 10.30.0.0/24 }
  web:
    type: OS::Nova::Server
    properties:
      image: ubuntu
      flavor: { get_param: flavor }
      networks: [ { subnet: { get_resource: subnet } } ]
outputs:
  web_ip:
    value: { get_attr: [web, first_address] }
\end{lstlisting}
Création : \texttt{openstack stack create -t web.yaml --parameter flavor=m1.medium web-stack}.
\end{correction}

\begin{exercice}{Ordre de création}\label{ex:he-ordre}
Un modèle contient \texttt{net}, \texttt{subnet} (qui référence \texttt{net}), \texttt{server} (qui référence \texttt{subnet}),
\texttt{volume} (sans référence) et \texttt{attach} (qui référence \texttt{server} et \texttt{volume}). Dans quel ordre Heat
crée-t-il les ressources ? Et à la suppression ?
\end{exercice}
\begin{correction}
\texttt{net} et \texttt{volume} n'ont aucune dépendance : ils sont créés en parallèle. Viennent ensuite \texttt{subnet}, puis
\texttt{server}, enfin \texttt{attach}, qui attend \texttt{server} et \texttt{volume}. La suppression suit l'ordre inverse :
\texttt{attach} d'abord, puis \texttt{server} et \texttt{volume} (en parallèle), puis \texttt{subnet}, puis \texttt{net}.
\end{correction}

\begin{exercice}{Mettre à jour une stack}\label{ex:he-maj}
Un serveur défini par un modèle est déployé. On modifie dans le modèle (a)~la valeur de \texttt{flavor}, puis
(b)~le contenu de \texttt{user\_data}. Que fait Heat par défaut dans chaque cas, et comment le vérifier avant d'agir ?
\end{exercice}
\begin{correction}
(a)~Le serveur est redimensionné (\texttt{flavor\_\allowbreak update\_\allowbreak policy} vaut \texttt{RESIZE} par défaut).
(b)~Le serveur est remplacé : supprimé et recréé, donc une nouvelle instance (\texttt{user\_\allowbreak data\_\allowbreak update\_\allowbreak policy}
vaut \texttt{REPLACE} par défaut). Vérification : \texttt{openstack stack update --dry-run}.
\end{correction}

\subsection{Récapitulatif du chapitre}\label{sec:he-recap}
% ---------------------------------------------------------------------

\begin{aretenir}
\begin{itemize}
  \item Heat crée, modifie et détruit une \gls{stack} à partir d'un modèle YAML (HOT), en appelant les API des autres services.
  \item Un modèle déclare des paramètres, des ressources (\texttt{OS::Service::Type}) et des sorties ; les fonctions
        \texttt{get\_param}, \texttt{get\_resource} et \texttt{get\_attr} les relient.
  \item Les références entre ressources forment un graphe de dépendances : création dans l'ordre, en parallèle quand c'est
        possible ; suppression dans l'ordre inverse.
  \item L'API (\texttt{heat-api}, \texttt{heat-api-cfn}) transmet au moteur (\texttt{heat-engine}) par RPC ; un trust permet
        les opérations différées.
  \item Une mise à jour met à jour en place ou remplace chaque ressource selon la propriété modifiée ; \texttt{--dry-run}
        montre le résultat avant d'agir.
  \item Groupes, mise à l'échelle, modèles imbriqués et configuration logicielle passent par des types de ressources dédiés.
\end{itemize}
\end{aretenir}

\renewcommand{\arraystretch}{1.35}
\begin{tabular}{@{}>{\raggedright\arraybackslash}p{4.2cm}>{\raggedright\arraybackslash}p{9.9cm}r@{}}
\toprule
\textbf{Tâche} & \textbf{Commande} & \textbf{§} \\
\midrule
Créer une stack & \texttt{openstack stack create -t T --parameter k=v S} & \ref{sec:he-cycle} \\
Suivre et diagnostiquer & \texttt{stack show}, \texttt{event list}, \texttt{resource list}, \texttt{failures list} & \ref{sec:he-deploiement} \\

\begin{itemize}
  \item Écrire un modèle HOT avec paramètre, contrainte, dépendances et sortie (exercice~\ref{ex:he-modele}).
  \item Déduire l'ordre de création et de suppression d'un graphe de ressources (exercice~\ref{ex:he-ordre}).
  \item Prévoir l'effet d'une mise à jour et le vérifier avec \texttt{--dry-run} (exercice~\ref{ex:he-maj}).
\end{itemize}
\end{savoirfaire}
