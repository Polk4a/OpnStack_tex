\section{Horizon : le tableau de bord}\label{chap:horizon}
% =====================================================================

Horizon est l'interface Web d'OpenStack. Ce chapitre présente son rôle, la façon dont il organise l'interface en
dashboards et en panneaux, son architecture, le parcours d'une requête, puis l'installation, la personnalisation, la
sécurisation et le dépannage.

% ---------------------------------------------------------------------
\subsection{Rôle et place d'Horizon}\label{sec:ho-role}
% ---------------------------------------------------------------------

\begin{definition}{Horizon}
Horizon est l'implémentation de référence du tableau de bord d'OpenStack : une interface Web qui donne accès aux
services (Nova, Cinder, Neutron, Glance, Swift, Keystone\dots) \parencite{horizon-docs}. C'est une application
\gls{django} qui appelle les API REST des services avec les droits de l'utilisateur connecté.
\end{definition}

\begin{itemize}
  \item \textbf{Problème.} Rendre la plateforme utilisable sans ligne de commande, par les utilisateurs d'un projet comme par
        les administrateurs.
  \item \textbf{Communique avec.} Keystone, indispensable pour la connexion, puis les API des autres services, que
        Horizon détecte automatiquement (Nova, Cinder, Glance, Neutron, Swift) \parencite{horizon-requirements} ; un cache
        pour conserver les sessions.
  \item \textbf{Exemple.} créer un volume dans le panneau \emph{Volumes} du dashboard \emph{Project} envoie à Cinder la
        même requête que la commande suivante :
\begin{lstlisting}[style=terminal]
$ openstack volume create --size 10 data-volume
\end{lstlisting}
\end{itemize}

Horizon n'est donc pas indispensable au fonctionnement de la plateforme : tout ce qu'il fait passe par les API REST, que la
CLI appelle aussi (support de cours, partie 10). Une action possible dans l'un l'est presque toujours dans l'autre.

Ce que l'utilisateur voit dépend de deux choses. D'abord des services installés : Horizon détecte automatiquement Cinder,
Glance, Neutron, Nova et Swift, et les autres services s'ajoutent par des plugins \parencite{horizon-requirements}, par
exemple pour Trove, Octavia ou Heat. Ensuite de ses rôles : les permissions d'un utilisateur dérivent des rôles que
Keystone lui attribue \parencite{horizon-auth-backend}, et un panneau peut exiger une permission ou une règle de \gls{policy}
\parencite{horizon-quickstart}. Ainsi, le dashboard \emph{Admin} est réservé aux administrateurs. Le dashboard est aussi
l'unité d'extension : on l'ajoute, on le désactive ou on lui retire un panneau par un fichier de configuration
(section~\ref{sec:ho-perso}).

% ---------------------------------------------------------------------
\subsection{Architecture d'Horizon}\label{sec:ho-archi}
% ---------------------------------------------------------------------

Le projet contient deux composants. Le répertoire \texttt{horizon} est une bibliothèque générique, utilisable dans n'importe
quel projet Django ; \texttt{openstack\_\allowbreak dashboard} est le projet Django de référence qui s'appuie sur elle et contient les
dashboards d'OpenStack \parencite{horizon-quickstart}. L'authentification est confiée au module \texttt{openstack\_\allowbreak auth}, un
backend d'authentification de Django qui interroge Keystone \parencite{horizon-auth-backend}. Un dashboard se déclare dans un fichier
\texttt{dashboard.py}, un panneau dans un \texttt{panel.py} accompagné de ses routes (\texttt{urls.py}), de ses vues
(\texttt{views.py}) et de ses gabarits \parencite{horizon-quickstart}. Une couche d'abstraction offre un accès homogène aux
API des services \parencite{horizon-intro}.

Horizon est une application \gls{wsgi} : sur Ubuntu, le paquet \texttt{openstack-dashboard} l'installe sous Apache, dont la
configuration se trouve dans \texttt{/etc/apache2/\allowbreak conf-available/\allowbreak openstack-dashboard.conf} \parencite{horizon-install}. Il ne
conserve pas l'état de la plateforme : instances, volumes et réseaux restent dans les services et leurs bases. Il lui faut
seulement un endroit où garder les sessions, le plus souvent un cache comme \gls{memcached}. Les panneaux sont, selon les cas,
rendus côté serveur par des gabarits Django ou construits dans le navigateur avec AngularJS \parencite{horizon-customizing}.

% ---------------------------------------------------------------------
\subsection{De la connexion à l'affichage d'un panneau}\label{sec:ho-requete}
% ---------------------------------------------------------------------

À la connexion, Horizon transmet les identifiants à Keystone, qui renvoie un \gls{token} et le \gls{catalogue} de services.
L'objet utilisateur d'\texttt{openstack\_\allowbreak auth} conserve ce token, le catalogue, le projet et les rôles
\parencite{horizon-auth-user} ; le navigateur ne reçoit qu'un cookie de session (figure~\ref{fig:ho-seq}). Ensuite, chaque
page se construit à partir d'appels aux API, avec le token de l'utilisateur.

\begin{remarque}[Horizon n'a pas de pouvoir propre]
Horizon agit avec le token de l'utilisateur connecté : il ne peut rien faire que ses rôles ne permettent déjà en ligne de
commande. Il peut masquer un bouton d'après les règles de \gls{policy}, mais c'est le service interrogé qui décide et, s'il
refuse, Horizon affiche simplement l'erreur.
\end{remarque}

% ---------------------------------------------------------------------
\subsection{Installation et configuration}\label{sec:ho-install}
% ---------------------------------------------------------------------

Il faut un endpoint Keystone accessible ; les autres services sont facultatifs \parencite{horizon-requirements}. Sur Ubuntu,
l'installation tient en quatre gestes \parencite{horizon-install} :

\begin{enumerate}
  \item installer le paquet : \texttt{apt install openstack-dashboard} ;
  \item éditer \texttt{/etc/\allowbreak openstack-dashboard/\allowbreak local\_\allowbreak settings.py} (listing ci-dessous) ;
  \item ajouter la ligne \texttt{WSGIApplicationGroup \%\{GLOBAL\}} au fichier \texttt{openstack-dashboard.conf} d'Apache
        (répertoire \texttt{/etc/apache2/conf-available}) ;
  \item recharger Apache : \texttt{systemctl reload apache2.service}.
\end{enumerate}

Le tableau de bord est alors accessible dans un navigateur à l'adresse \texttt{http://controller/horizon} ; on s'y connecte,
par exemple, avec l'utilisateur \texttt{admin} et le domaine \texttt{default} \parencite{horizon-verify}.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
# /etc/openstack-dashboard/local_settings.py (extrait)
OPENSTACK_HOST = "controller"
ALLOWED_HOSTS = ['one.example.com', 'two.example.com']
SESSION_ENGINE = 'django.contrib.sessions.backends.cache'
CACHES = {
    'default': {
        'BACKEND': 'django.core.cache.backends.memcached.PyMemcacheCache',
        'LOCATION': 'controller:11211',
    }
}
OPENSTACK_KEYSTONE_URL = "http://%s/identity/v3" % OPENSTACK_HOST
OPENSTACK_KEYSTONE_MULTIDOMAIN_SUPPORT = True
OPENSTACK_KEYSTONE_DEFAULT_DOMAIN = "Default"
OPENSTACK_API_VERSIONS = {"identity": 3, "image": 2, "volume": 3}
TIME_ZONE = "Europe/Paris"
\end{lstlisting}
\end{minipage}\par

L'application relit ce fichier quand Apache est rechargé. Le tableau~\ref{tab:ho-reglages} décrit les réglages les plus
utiles ; les valeurs par défaut viennent de la référence \parencite{horizon-settings}. Pour séparer la configuration locale,
on peut aussi déposer des fragments \texttt{.py} dans le répertoire \texttt{openstack\_\allowbreak dashboard/local/local\_\allowbreak settings.d/}
(nom commençant par un tiret bas ; ils sont lus par ordre alphabétique après \texttt{local\_\allowbreak settings.py}).

\subsection{Personnaliser : panneaux, thèmes et identité visuelle}\label{sec:ho-perso}

ordre alphabétique, et les fichiers locaux l'emportent ; le nom commence par un tiret bas et un nombre, qui fixe l'ordre
\parencite{horizon-panels}. Les variables utiles sont résumées dans le tableau~\ref{tab:ho-enabled}. Exemple :

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
# openstack_dashboard/local/enabled/_9000_admin_info_remove.py
PANEL = 'info'
PANEL_DASHBOARD = 'admin'
PANEL_GROUP = 'admin'
REMOVE_PANEL = True
\end{lstlisting}
\end{minipage}\par

Ce fichier retire le panneau \emph{System Information} du dashboard \emph{Admin} sans toucher au code d'Horizon : son numéro
élevé le fait lire après ceux qui déclarent le panneau. Pour renommer un panneau, retirer des colonnes d'un tableau ou
remplacer une méthode, on déclare un module de personnalisation : la clé \texttt{customization\_\allowbreak module} de
\texttt{HORIZON\_\allowbreak CONFIG} désigne alors un module Python à nous \parencite{horizon-customizing}.

\paragraph{Thèmes et marque.} Un thème est un répertoire qui contient au moins un sous-répertoire \texttt{static} avec deux
fichiers SCSS : \texttt{\_variables.scss} (couleurs et variables Bootstrap) et \texttt{\_styles.scss} (styles ajoutés après ceux
du tableau de bord) ; on peut y joindre des gabarits (\texttt{templates/}) et des images (\texttt{img/logo.svg},
\texttt{favicon.ico}\dots). Horizon fournit deux thèmes, \texttt{default} et \texttt{material}. Après une modification, on régénère les
fichiers statiques avec \texttt{manage.py collectstatic} \parencite{horizon-themes}. Le titre et le lien du logo se règlent dans
\texttt{local\_\allowbreak settings.py} \parencite{horizon-customizing}.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
SITE_BRANDING = "Cloud pédagogique"
SITE_BRANDING_LINK = "https://www.insa-cvl.fr"
AVAILABLE_THEMES = [
    ('default', 'Default', 'themes/default'),
    ('insa', 'Thème INSA CVL', 'themes/insa'),
]
DEFAULT_THEME = 'insa'
\end{lstlisting}
\end{minipage}\par

Dans \texttt{AVAILABLE\_\allowbreak THEMES}, chaque triplet donne la clé du thème (mémorisée dans un cookie), son libellé dans le menu
de l'utilisateur et son chemin, relatif à \texttt{openstack\_\allowbreak dashboard} ou absolu \parencite{horizon-themes}.

\subsection{Sécuriser et dépanner}\label{sec:ho-securite}
% ---------------------------------------------------------------------

Le tableau de bord est la porte d'entrée de la plateforme : il doit être servi en HTTPS. Le guide de sécurité d'OpenStack
recommande les réglages du tableau~\ref{tab:ho-secu}. Un cookie \emph{secure} n'est envoyé que par une connexion chiffrée ;
un cookie \emph{HttpOnly} est inaccessible aux scripts de la page \parencite{security-guide-dashboard}. Le fichier
\texttt{local\_\allowbreak settings.py} contient des secrets : il appartient à \texttt{root}, au groupe \texttt{horizon}, avec les droits
\texttt{640} ou plus stricts.

\subsection{Exercices corrigés}\label{sec:ho-exercices}
% ---------------------------------------------------------------------

\begin{exercice}{Même action, deux chemins}\label{ex:ho-chemins}
Un utilisateur crée un volume de 10~Go dans Horizon, puis refait la même opération en ligne de commande. (a)~Qu'ont ces
deux actions en commun, et qu'est-ce qui change ? (b)~Où Horizon trouve-t-il l'adresse de Cinder ? (c)~Que se passe-t-il si
l'utilisateur n'a pas le droit de créer un volume ?
\end{exercice}
\begin{correction}
(a)~Les deux envoient la même requête REST à l'API de Cinder (\texttt{POST} sur \texttt{/v3/volumes}), avec le token de
l'utilisateur. Seul le client change : Horizon appelle depuis le serveur web, la CLI depuis le poste de l'utilisateur.
(b)~Dans le catalogue de services reçu de Keystone à la connexion et conservé en session ; l'endpoint retenu dépend de
\texttt{OPENSTACK\_\allowbreak ENDPOINT\_\allowbreak TYPE} (\texttt{publicURL} par défaut). (c)~Cinder applique ses règles de \gls{policy} et refuse la
requête ; Horizon affiche l'erreur, car il n'a pas de droits propres.
\end{correction}

\begin{exercice}{Déployer sur deux serveurs}\label{ex:ho-deploiement}
Horizon tourne sur deux serveurs derrière un répartiteur de charge qui termine le HTTPS ; les utilisateurs sont
déconnectés au hasard. (a)~Quelle est la cause probable ? (b)~Quels réglages modifier dans \texttt{local\_\allowbreak settings.py}, et quels
réglages de sécurité ajouter ?
\end{exercice}
\begin{correction}
(a)~Les sessions sont gardées en mémoire locale : une requête servie par l'autre serveur ne retrouve pas la session.
(b)~Il faut un stockage partagé, par exemple un memcached commun, et les réglages de sécurité des cookies. Comme le
répartiteur termine le HTTPS, \texttt{SECURE\_\allowbreak PROXY\_\allowbreak SSL\_\allowbreak HEADER} indique à Django comment reconnaître une requête sûre.
\begin{lstlisting}
SESSION_ENGINE = 'django.contrib.sessions.backends.cache'
CACHES = {'default': {
    'BACKEND': 'django.core.cache.backends.memcached.PyMemcacheCache',
    'LOCATION': 'memcache.example.org:11211'}}
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
ALLOWED_HOSTS = ['cloud.example.org']
\end{lstlisting}
\end{correction}

\begin{exercice}{Retirer un panneau}\label{ex:ho-panneau}
On veut retirer le panneau \texttt{info} du dashboard \texttt{admin}, sans modifier le code d'Horizon. Quel fichier créer, où,
et que faire pour que le changement soit pris en compte ?
\end{exercice}
\begin{correction}
Créer un fichier \emph{enabled} dans \texttt{openstack\_\allowbreak dashboard/local/enabled}, par exemple
\texttt{\_9000\_\allowbreak admin\_\allowbreak info\_\allowbreak remove.py}, qui contient \texttt{PANEL = 'info'}, \texttt{PANEL\_\allowbreak DASHBOARD = 'admin'},
\texttt{PANEL\_\allowbreak GROUP = 'admin'} et \texttt{REMOVE\_\allowbreak PANEL = True}. Le numéro élevé garantit qu'il est lu après les fichiers qui
déclarent le panneau. Recharger Apache (\texttt{systemctl reload apache2.service}) pour que l'application relise sa configuration.
\end{correction}

\subsection{Récapitulatif du chapitre}\label{sec:ho-recap}
% ---------------------------------------------------------------------

\begin{aretenir}
\begin{itemize}
  \item Horizon est une application Django qui appelle les API REST des services avec le token de l'utilisateur ; elle n'a
        pas de pouvoir propre et ne conserve pas l'état de la plateforme.
  \item L'interface est organisée en dashboards (\emph{Project}, \emph{Admin}, \emph{Identity}, \emph{Settings}) qui contiennent
        des panneaux ; ce que l'on voit dépend des services installés et des rôles.
  \item Le projet comprend la bibliothèque \texttt{horizon}, le projet \texttt{openstack\_\allowbreak dashboard} et le module
        d'authentification \texttt{openstack\_\allowbreak auth}.
  \item À la connexion, Keystone délivre un token et le catalogue ; ils restent en session, et le navigateur ne reçoit qu'un
        cookie.
  \item La configuration tient dans \texttt{local\_\allowbreak settings.py} ; avec plusieurs serveurs, les sessions doivent être
        partagées (memcached, base de données).
  \item Panneaux et dashboards se modifient par des fichiers \emph{enabled} ; l'apparence, par des thèmes.
  \item Servir le tableau de bord en HTTPS, avec des cookies \emph{secure} et \emph{HttpOnly}.
\end{itemize}
\end{aretenir}
