\section{Octavia : la répartition de charge}\label{chap:octavia}
% =====================================================================

Octavia permet de présenter une application répartie sur plusieurs instances derrière une adresse unique. Ce chapitre
présente son rôle, les objets qu'il manipule (répartiteur, listener, pool, members), son architecture, la création d'un
répartiteur, la surveillance de la santé et la haute disponibilité, les fonctions avancées (TLS, persistance) et la mise
en œuvre.

% ---------------------------------------------------------------------
\subsection{Rôle et place d'Octavia}\label{sec:oc-role}
% ---------------------------------------------------------------------

\begin{definition}{Octavia}
Octavia est le service de répartition de charge d'OpenStack. C'est une solution libre, conçue pour fonctionner avec
OpenStack à l'échelle d'un opérateur : elle distribue le trafic entrant vers un groupe de serveurs et cesse d'envoyer des
requêtes à ceux qui ne répondent plus \parencite{octavia-intro}.
\end{definition}

\begin{itemize}
  \item \textbf{Problème.} Faire évoluer une application Web sur plusieurs instances tout en gardant un point d'accès
        unique et une haute disponibilité (support de cours, partie 12).
  \item \textbf{Communique avec.} Keystone (authentification), Nova (les instances qui font le travail de répartition),
        Neutron (l'adresse du service et les réseaux), Glance (l'image de ces instances) et Barbican (les certificats
        TLS) \parencite{octavia-intro}.
  \item \textbf{Exemple.} créer un répartiteur sur un sous-réseau :
\begin{lstlisting}[style=terminal]
$ openstack loadbalancer create --name lb1 --vip-subnet-id public-subnet --wait
\end{lstlisting}
\end{itemize}

\subsection{Concepts : du répartiteur aux members}\label{sec:oc-concepts}
% ---------------------------------------------------------------------

Un répartiteur est décrit par quelques objets emboîtés (tableau~\ref{tab:oc-objets} et figure~\ref{fig:oc-flux}). Le trafic
arrive sur une adresse de service, le \gls{vip} ; un \gls{listener} écoute un protocole et un port ; il transmet les requêtes
à un \gls{poolocta}, dont les \glspl{memberocta} sont les serveurs réels, surveillés par un \gls{healthmonitor}
\parencite{octavia-glossary}.

\subsection{Architecture interne}\label{sec:oc-archi}
% ---------------------------------------------------------------------

Octavia se compose d'un contrôleur, de machines virtuelles qui répartissent le trafic, les \glspl{amphore}, et d'un réseau
qui les relie au contrôleur \parencite{octavia-intro}. L'implémentation de référence d'une amphore est une instance Nova
qui exécute \gls{haproxy} \parencite{octavia-intro, octavia-components}. Le contrôleur est formé de plusieurs processus
(tableau~\ref{tab:oc-composants}, figure~\ref{fig:oc-archi}).

\textrm{\textbf{Composant}} & \textbf{Rôle} \\
\midrule
octavia-api & Reçoit les requêtes REST (port 9876) et les transmet par la messagerie. \\

octavia-housekeeping & Nettoie la base de données et gère la rotation des certificats. \\

Le contrôleur dialogue avec une amphore par une API REST en HTTPS à authentification mutuelle ; l'amphore lui envoie des
messages de santé courts et périodiques en UDP, signés par HMAC \parencite{octavia-components}. Les certificats se règlent
dans \texttt{[haproxy\_\allowbreak amphora]} (\texttt{client\_\allowbreak cert}, \texttt{server\_\allowbreak ca}) et la clé des heartbeats dans
\texttt{[health\_\allowbreak manager]} (\texttt{heartbeat\_\allowbreak key}) \parencite{octavia-config}.

Le service s'appuie sur des \emph{drivers} : le driver \texttt{amphora}, pilote de référence, est le choix par défaut
(\texttt{default\_\allowbreak provider\_\allowbreak driver}) ; d'autres pilotes (OVN, F5, A10, Radware, VMware NSX) remplacent l'amphore par
une autre implémentation \parencite{octavia-providers, octavia-config}.

\subsection{Créer un répartiteur de charge}\label{sec:oc-creation}
% ---------------------------------------------------------------------

La création est asynchrone : l'API répond aussitôt, avec un objet à l'état \texttt{PENDING\_\allowbreak CREATE}, puis le
\emph{controller worker} fait créer l'amphore et la configure (figure~\ref{fig:oc-seq}). L'option \texttt{--wait} des
commandes attend la fin de l'opération.

\label{fig:oc-seq}

Un répartiteur HTTP minimal se construit en cinq commandes, dans l'ordre des objets : répartiteur, listener, pool,
members, health monitor \parencite{octavia-cookbook}.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ openstack loadbalancer create --name lb1 --vip-subnet-id public-subnet --wait
$ openstack loadbalancer listener create --name listener1 --protocol HTTP \
    --protocol-port 80 --wait lb1
$ openstack loadbalancer pool create --name pool1 --lb-algorithm ROUND_ROBIN \
    --listener listener1 --protocol HTTP --wait
$ openstack loadbalancer member create --subnet-id private-subnet \
    --address 192.0.2.10 --protocol-port 80 --wait pool1
$ openstack loadbalancer member create --subnet-id private-subnet \
    --address 192.0.2.11 --protocol-port 80 --wait pool1
$ openstack loadbalancer healthmonitor create --delay 5 --max-retries 4 \
    --timeout 10 --type HTTP --url-path /healthcheck --wait pool1
\end{lstlisting}
\end{minipage}\par

Le VIP est une adresse du réseau choisi à la création (\texttt{--vip-subnet-id}). Pour joindre le service depuis
l'extérieur, on associe une IP flottante au port du VIP \parencite{octavia-cookbook} :

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ openstack floating ip create public
$ openstack floating ip set --port <load_balancer_vip_port_id> <floating_ip_id>
\end{lstlisting}
\end{minipage}\par

% ---------------------------------------------------------------------
\subsection{Santé et haute disponibilité}\label{sec:oc-sante}
% ---------------------------------------------------------------------

Deux surveillances se superposent (figure~\ref{fig:oc-sante}). La première concerne les \emph{members} : le health monitor
les sonde toutes les \texttt{--delay} secondes ; si un member échoue, il est retiré du pool et passe en \texttt{ERROR}, puis
il revient en \texttt{ONLINE} dès qu'il répond de nouveau \parencite{octavia-cookbook}. Les types de sonde sont \texttt{HTTP},
\texttt{HTTPS}, \texttt{PING}, \texttt{TCP}, \texttt{TLS-HELLO}, \texttt{UDP-CONNECT} et \texttt{SCTP}
\parencite{octavia-api-ref}. La seconde concerne les \emph{amphores} : chacune envoie des heartbeats au health manager ;
si l'un d'eux manque au-delà de \texttt{heartbeat\_\allowbreak timeout} (60~s par défaut), l'amphore est remplacée
\parencite{octavia-config}.

\label{fig:oc-sante}

La \emph{topologie} fixe le nombre d'amphores par répartiteur : \texttt{SINGLE} (une, valeur par défaut) ou
\texttt{ACTIVE\_\allowbreak STANDBY} (deux, dont une de secours) \parencite{octavia-config}. L'administrateur la propose aux
utilisateurs par des \emph{flavors} de répartiteur \parencite{octavia-flavors}, et peut forcer le remplacement d'une amphore :

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ openstack loadbalancer flavorprofile create --name amphora-single-profile \
    --provider amphora --flavor-data '{"loadbalancer_topology": "SINGLE"}'
$ openstack loadbalancer flavor create --name standalone-lb \
    --flavorprofile amphora-single-profile --enable
$ openstack loadbalancer failover lb1
\end{lstlisting}
\end{minipage}\par

Après un \texttt{failover}, on suit l'opération avec \texttt{openstack loadbalancer show} jusqu'au retour à l'état
\texttt{ACTIVE} \parencite{octavia-maintenance}.

Pour terminer le TLS sur le répartiteur, on stocke d'abord le certificat et sa clé dans Barbican, au format PKCS\,\#12,
puis on crée un listener qui y fait référence \parencite{octavia-cookbook} :

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ openssl pkcs12 -export -inkey server.key -in server.crt \
    -certfile ca-chain.crt -passout pass: -out server.p12
$ openstack secret store --name='tls_secret1' -t 'application/octet-stream' \
    -e 'base64' --payload="$(base64 < server.p12)"
$ openstack loadbalancer listener create --protocol-port 443 \
    --protocol TERMINATED_HTTPS --name listener-https --default-pool pool1 \
    --default-tls-container=$(openstack secret list | awk '/ tls_secret1 / {print $2}') \
    --wait lb1
\end{lstlisting}
\end{minipage}\par

Sur le contrôleur, l'installation crée une base \texttt{octavia}, l'utilisateur \texttt{octavia} dans Keystone, le service de
type \texttt{load-balancer} avec ses trois endpoints sur \texttt{http://controller:9876}, puis installe les paquets
\texttt{octavia-api}, \texttt{octavia-health-manager}, \texttt{octavia-housekeeping} et \texttt{octavia-worker}. Il faut aussi

Glance avec une étiquette que \texttt{amp\_\allowbreak image\_\allowbreak tag} reprend \parencite{octavia-maintenance}.

\subsection{Exercices corrigés}\label{sec:oc-exercices}
% ---------------------------------------------------------------------

\begin{exercice}{Un site sur deux instances}\label{ex:oc-site}
Deux instances \texttt{10.0.0.11} et \texttt{10.0.0.12} (sous-réseau \texttt{private-subnet}) servent un site HTTP sur le
port 80 ; le VIP doit être pris sur \texttt{public-subnet}. Écrire les commandes qui créent le répartiteur \texttt{web-lb},
répartissent à tour de rôle et surveillent la page \texttt{/health}. Comment le rendre joignable depuis Internet ?
\end{exercice}
\begin{correction}
\begin{lstlisting}[style=terminal]
$ openstack loadbalancer create --name web-lb \
    --vip-subnet-id public-subnet --wait
$ openstack loadbalancer listener create --name web-http --protocol HTTP \
    --protocol-port 80 --wait web-lb
$ openstack loadbalancer pool create --name web-pool \
    --lb-algorithm ROUND_ROBIN --listener web-http --protocol HTTP --wait
$ openstack loadbalancer member create --subnet-id private-subnet \
    --address 10.0.0.11 --protocol-port 80 --wait web-pool
$ openstack loadbalancer member create --subnet-id private-subnet \
    --address 10.0.0.12 --protocol-port 80 --wait web-pool
$ openstack loadbalancer healthmonitor create --delay 5 --max-retries 4 \
    --timeout 10 --type HTTP --url-path /health --wait web-pool
\end{lstlisting}
Pour l'ouvrir à Internet : créer une IP flottante et l'associer au port du VIP (\texttt{openstack floating ip set --port}).
\end{correction}

\begin{exercice}{Lire les statuts}\label{ex:oc-statuts}
Un répartiteur affiche \texttt{provisioning\_status = ACTIVE} et \texttt{operating\_status = DEGRADED}. Que signifient ces
deux valeurs, et que vérifier ?
\end{exercice}
\begin{correction}
\texttt{ACTIVE} : le répartiteur a été créé correctement. \texttt{DEGRADED} : au moins un de ses composants est en erreur ;
ici, très probablement, un member qui échoue au health monitor. On le repère avec
\texttt{openstack loadbalancer status show} ou \texttt{member list}, puis on vérifie que le serveur répond sur son port, que
le chemin de test existe et que son groupe de sécurité accepte le trafic venant de l'amphore.
\end{correction}

\begin{exercice}{Panne d'une amphore}\label{ex:oc-panne}
La machine hôte d'une amphore tombe en panne. Que se passe-t-il, au bout de combien de temps, et comment forcer l'opération ?
\end{exercice}
\begin{correction}
Les heartbeats cessent d'arriver au health manager. Passé \texttt{heartbeat\_\allowbreak timeout} (60~s par défaut), il déclenche le
remplacement : le worker recrée une amphore avec la configuration du répartiteur. Le service est interrompu pendant cette
durée avec la topologie \texttt{SINGLE} ; \texttt{ACTIVE\_\allowbreak STANDBY} garde une amphore de secours. On peut forcer
l'opération avec \texttt{openstack loadbalancer failover lb1}, puis attendre le retour à \texttt{ACTIVE}.
\end{correction}

\subsection{Récapitulatif du chapitre}\label{sec:oc-recap}
% ---------------------------------------------------------------------

\begin{aretenir}
\begin{itemize}
  \item Octavia répartit le trafic d'un VIP vers les members d'un pool, par des amphores : des instances Nova qui
        exécutent HAProxy.
  \item Les objets s'emboîtent : répartiteur, listener, pool, members, health monitor ; les politiques L7 aiguillent selon
        l'URL.
  \item Le contrôleur (API, worker, health manager, housekeeping) pilote les amphores par un réseau de gestion en HTTPS ;
        elles envoient des heartbeats en UDP.
  \item La création est asynchrone : \texttt{PENDING\_\allowbreak CREATE} puis \texttt{ACTIVE} ; le statut opérationnel indique
        la santé (\texttt{ONLINE}, \texttt{DEGRADED}, \texttt{ERROR}\dots).
  \item Un member défaillant est écarté par le health monitor ; une amphore défaillante est remplacée (\emph{failover}).
  \item Le TLS peut être terminé sur le répartiteur (certificat dans Barbican) ou laissé aux serveurs.
\end{itemize}
\end{aretenir}
