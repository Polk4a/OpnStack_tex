\section{Ironic : le bare metal en tant que service}\label{chap:ironic}
% =====================================================================

Ironic fait des serveurs physiques une ressource du cloud : on les enregistre, puis on les attribue comme des instances.
Ce chapitre présente son rôle, ses concepts (nœud, port, type de matériel, classe de ressources), son architecture, la machine
à états d'un nœud, l'enrôlement et le déploiement, le nettoyage entre deux locataires, le réseau et la mise en œuvre \parencite{ironic-index}.

% ---------------------------------------------------------------------
\subsection{Rôle et place d'Ironic}\label{sec:ir-role}
% ---------------------------------------------------------------------

\begin{definition}{Ironic}
Ironic est le service Bare Metal d'OpenStack. Il provisionne des serveurs \gls{baremetal}, c'est-à-dire des machines physiques
dédiées à un seul utilisateur, sans hyperviseur : il gère leur inventaire, leur alimentation, leur démarrage par le réseau,
l'écriture d'une image sur leur disque et leur remise en état. Avec Nova, il présente un serveur physique comme une instance
\parencite{ironic-overview}.
\end{definition}

\begin{itemize}
  \item \textbf{Problème.} Certaines charges ne s'accommodent pas d'un hyperviseur : calcul haute performance, accès à du
        matériel qu'on ne sait pas virtualiser, bases de données, exigences d'isolation ou de matériel dédié, ou déploiement du
        cloud lui-même \parencite{ironic-overview}.
  \item \textbf{Communique avec.} Keystone (authentification), Nova (API utilisateur et ordonnancement), Glance (images),
        Neutron (DHCP et réseaux) et Swift (stockage temporaire de l'image, du \emph{config drive} et des journaux)
        \parencite{ironic-overview}.
  \item \textbf{Exemple.} pour l'utilisateur, une instance bare metal se commande comme une machine virtuelle :
\begin{lstlisting}[style=terminal]
$ openstack server create --flavor baremetal-gpu --image ubuntu \
    --network provider bm-instance
\end{lstlisting}
\end{itemize}

\subsection{Architecture}\label{sec:ir-archi}
% ---------------------------------------------------------------------

(tableau~\ref{tab:ir-composants} et figure~\ref{fig:ir-archi}). L'API transmet les requêtes au \gls{conductorironic} par RPC ;
c'est lui qui agit sur le matériel, au moyen de pilotes \parencite{ironic-overview}.

Comme les autres services, Ironic utilise une base de données et une file de messages compatible \texttt{oslo.messaging}
(RabbitMQ) pour le RPC entre l'API et les conductors ; un transport JSON-RPC peut remplacer la file
(\texttt{rpc\_\allowbreak transport = json-rpc}) \parencite{ironic-overview,ironic-install}. Chaque conductor gère une partie des
nœuds, distribuée par un anneau de hachage (\emph{hash ring}) ; il en surveille régulièrement l'alimentation, doit joindre le
contrôleur de gestion (\gls{bmc}) de chacun et fournit, par TFTP ou HTTP, le noyau et le ramdisk de démarrage
\parencite{ironic-refarch}. Tous les conductors doivent être à la même version \parencite{ironic-install}.

Le conductor agit sur le matériel par des pilotes. Un \gls{hardwaretype} assemble des \glspl{interfacemat}, une par aspect
du serveur (tableau~\ref{tab:ir-interfaces}). Les types génériques sont \texttt{ipmi} et \texttt{redfish} (\gls{ipmi},
\gls{redfish}) ; certains constructeurs en ont d'autres. On les active dans la configuration du conductor
(\texttt{enabled\_\allowbreak hardware\_\allowbreak types}) et chaque nœud choisit son type à sa création
\parencite{ironic-drivers}.

% ---------------------------------------------------------------------
\subsection{Enrôler un nœud et l'offrir à Nova}\label{sec:ir-enrol}
% ---------------------------------------------------------------------

Enrôler un nœud, c'est le déclarer à Ironic, puis le faire passer de \texttt{enroll} à \texttt{available}
\parencite{ironic-enrollment,osc-baremetal}. On crée le nœud avec son type de matériel et les informations de gestion : adresse et
identifiants du BMC, noyau et ramdisk de déploiement (ils peuvent aussi être fixés pour tous les nœuds dans la
configuration du conductor \parencite{ironic-glance-images}). On déclare chaque carte réseau par un port et l'on attribue au
nœud une classe de ressources.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ NODE=$(openstack baremetal node create --driver ipmi \
    --name gpu-node-01 --resource-class baremetal-gpu \
    --driver-info ipmi_address=10.0.0.21 \
    --driver-info ipmi_username=admin --driver-info ipmi_password=SECRET \
    --driver-info deploy_kernel=$KERNEL_UUID \
    --driver-info deploy_ramdisk=$RAMDISK_UUID \
    -f value -c uuid)
$ openstack baremetal port create AA:BB:CC:DD:EE:01 --node $NODE
$ openstack baremetal node validate $NODE
$ openstack baremetal node manage $NODE
$ openstack baremetal node provide $NODE
$ openstack baremetal node show $NODE -c provision_state -c last_error
\end{lstlisting}
\end{minipage}\par

\texttt{manage} et \texttt{provide} sont asynchrones : on suit leur résultat avec \texttt{node show}, dont le champ
\texttt{last\_\allowbreak error} explique un échec. \texttt{validate} contrôle chaque interface ; une erreur sur l'interface de
déploiement faute d'informations d'image est normale quand Nova les fournit au moment du déploiement
\parencite{ironic-enrollment}. \texttt{provide} lance le nettoyage automatique (section~\ref{sec:ir-nettoyage}).

Du côté de Nova, chaque nœud \texttt{available} apparaît comme un hôte distinct (hyperviseur de type \texttt{ironic}) et, pour
Placement, comme un fournisseur de ressources dont l'identifiant est celui du nœud \parencite{ironic-troubleshooting}. Le
flavor demande exactement une unité de la classe de ressources du nœud \parencite{ironic-nova-flavors}.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ openstack flavor create --ram 262144 --vcpus 32 --disk 960 \
    baremetal-gpu
$ openstack flavor set baremetal-gpu \
    --property resources:CUSTOM_BAREMETAL_GPU=1 \
    --property resources:VCPU=0 \
    --property resources:MEMORY_MB=0 \
    --property resources:DISK_GB=0
\end{lstlisting}
\end{minipage}\par

Le nom de la classe est celui du nœud, en majuscules, préfixé par \texttt{CUSTOM\_} et avec la ponctuation remplacée par des
soulignés : \texttt{baremetal-gpu} devient \texttt{CUSTOM\_\allowbreak BAREMETAL\_\allowbreak GPU}. Les trois propriétés à zéro
désactivent l'ordonnancement sur les ressources standard ; la mémoire et le nombre de processeurs du flavor ne servent qu'à
informer l'utilisateur, et le disque à dimensionner la partition racine. On peut aussi exiger des traits
(\texttt{trait:HW\_CPU\_X86\_VMX=required}) \parencite{ironic-nova-flavors}.

% ---------------------------------------------------------------------
\subsection{Déploiement et nettoyage}\label{sec:ir-nettoyage}
% ---------------------------------------------------------------------

La figure~\ref{fig:ir-seq} montre un déploiement par démarrage réseau. Il comporte deux cycles d'alimentation : le premier
démarre le ramdisk de déploiement (\gls{pxe} : DHCP, puis TFTP ou HTTP), le second le système installé
\parencite{ironic-overview}. Le ramdisk exécute l'agent \gls{ipa}, qui appelle l'API d'Ironic pour recevoir ses ordres ;
avec l'interface de déploiement \texttt{direct}, il télécharge lui-même l'image depuis une URL HTTP, par exemple une URL
temporaire de Swift \parencite{ironic-deploy-interfaces}.

Quand l'instance est supprimée, le nœud passe par \texttt{deleting} puis par le \gls{nettoyage} avant de redevenir
\texttt{available}. Le nettoyage automatique s'exécute aussi la première fois qu'un nœud passe de \texttt{manageable} à
\texttt{available} \parencite{ironic-cleaning}. Il est activé par défaut (\texttt{[conductor] automated\_\allowbreak clean = true})
et demande un réseau de nettoyage (\texttt{[neutron] cleaning\_\allowbreak network}) \parencite{ironic-configure-cleaning}. Ses
étapes viennent des interfaces matérielles, classées par priorité ; donner la priorité zéro à une étape la désactive
(tableau~\ref{tab:ir-nettoyage}).

Par défaut, Ironic exécute \texttt{erase\_\allowbreak devices\_\allowbreak metadata} tôt, pour qu'un nœud ne puisse pas redémarrer
sur son ancienne charge, puis \texttt{erase\_\allowbreak devices} \parencite{ironic-cleaning}. Si le nettoyage échoue, le nœud passe en
\texttt{clean failed} ; si l'échec survient pendant une étape, il est aussi mis en maintenance, et il n'est pas éteint. On n'en
sort que par \texttt{manage} (état \texttt{manageable}) : on y répare le nœud, puis on le rend avec \texttt{maintenance unset}
et \texttt{provide} (exercice~\ref{ex:ir-clean}). Le nettoyage manuel, lui, est lancé par l'opérateur.

% ---------------------------------------------------------------------
\subsection{Réseau et inspection}\label{sec:ir-reseau}
% ---------------------------------------------------------------------

L'interface réseau du nœud décide de son raccordement \parencite{ironic-networking} :

\begin{itemize}
  \item \texttt{noop} : aucune commutation ; pour les déploiements sans Neutron ;
  \item \texttt{flat} : tous les nœuds restent branchés sur un même réseau fournisseur, préconfiguré ;
  \item \texttt{neutron} : réseaux de locataires isolés. Le nœud passe du réseau de nettoyage au réseau de provisionnement,
        puis au réseau du locataire, et les commutateurs sont reprogrammés par un plugin ML2.
\end{itemize}

Avec \texttt{neutron}, le port d'Ironic porte les informations de liaison (\texttt{local\_\allowbreak link\_\allowbreak connection}) qui
indiquent à Neutron à quel port de commutateur le serveur est branché. Les réseaux de provisionnement et de nettoyage doivent
être réservés à Ironic (non partagés, projet \texttt{admin}) et laisser passer DHCP, TFTP, l'accès à l'API (port 6385) et
l'accès à l'agent (port 9999) \parencite{ironic-networking,ironic-tenant-networks}.

L'\emph{inspection} relève les propriétés matérielles d'un nœud (mémoire, disque, architecture\dots) et crée ses ports. Elle
part de l'état \texttt{manageable} (\texttt{openstack baremetal node inspect}). Elle se fait hors bande, par le BMC (types
\texttt{redfish}, \texttt{idrac}), ou en bande, par l'agent dans un ramdisk : plus longue et plus fragile, mais indépendante du constructeur
\parencite{ironic-inspection}.

\subsection{Mise en œuvre et dépannage}\label{sec:ir-deploiement}
% ---------------------------------------------------------------------

L'installation suppose Keystone, Glance, Nova et Neutron en place. On crée la base \texttt{ironic} (en \texttt{utf8mb4}),
l'utilisateur \texttt{ironic} (rôle \texttt{admin} du projet \texttt{service}), le service \texttt{baremetal} et ses trois
endpoints (port 6385) et, pour déléguer des droits limités, les rôles \texttt{baremetal\_\allowbreak admin} et
\texttt{baremetal\_\allowbreak observer} \parencite{ironic-identity,ironic-install}. On installe \texttt{ironic-api},
\texttt{ironic-conductor}, \texttt{ironic-novncproxy} et \texttt{python3-ironicclient}, puis on configure le service. Le
serveur du conductor fournit aussi TFTP ou HTTP, et \texttt{ipmitool} pour les nœuds IPMI \parencite{ironic-pxe,ironic-ipmi}.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
# /etc/ironic/ironic.conf (extrait)
[DEFAULT]
my_ip = 10.0.0.11
transport_url = rabbit://openstack:RABBIT_PASS@controller
enabled_hardware_types = ipmi,redfish
enabled_network_interfaces = flat,neutron
default_network_interface = neutron
[database]
connection = mysql+pymysql://ironic:IRONIC_DBPASS@controller/ironic
[conductor]
automated_clean = true
[neutron]
provisioning_network = provisioning
cleaning_network = cleaning
\end{lstlisting}
\end{minipage}\par

On crée le schéma de la base avec \texttt{ironic-dbsync --config-file /etc/ironic/ironic.conf create\_\allowbreak schema}, puis on
redémarre \texttt{ironic-api} et \texttt{ironic-conductor} \parencite{ironic-install}. Nova doit utiliser le pilote Ironic, sur
le contrôleur et sur le nœud de calcul qui représente les serveurs physiques \parencite{ironic-nova-compute} :

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
# /etc/nova/nova.conf (extrait)

reserved_host_memory_mb = 0
[filter_scheduler]
track_instance_changes = False
[scheduler]
discover_hosts_in_cells_interval = 120
[ironic]
auth_type = password
auth_url = http://controller:5000/v3
project_name = service
username = ironic

\subsection{Exercices corrigés}\label{sec:ir-exercices}
% ---------------------------------------------------------------------

\begin{exercice}{Enrôler un serveur}\label{ex:ir-enrol}
Un serveur physique \texttt{srv-db-01} (BMC IPMI à l'adresse \texttt{10.0.0.31}, identifiants \texttt{admin} et \texttt{SECRET},
deux cartes réseau d'adresses MAC \texttt{52:54:00:00:00:01} et \texttt{52:54:00:00:00:02}) doit être proposé aux utilisateurs
avec la classe \texttt{baremetal-db}. Le noyau et le ramdisk de déploiement sont déjà fixés dans la configuration du
conductor. Écrire les commandes qui l'amènent à l'état \texttt{available}, puis celles qui créent le flavor \texttt{bm.db}
associé.
\end{exercice}
\begin{correction}
\begin{lstlisting}
$ NODE=$(openstack baremetal node create --driver ipmi \
    --name srv-db-01 --resource-class baremetal-db \
    --driver-info ipmi_address=10.0.0.31 \
    --driver-info ipmi_username=admin \
    --driver-info ipmi_password=SECRET -f value -c uuid)
$ openstack baremetal port create 52:54:00:00:00:01 --node $NODE
$ openstack baremetal port create 52:54:00:00:00:02 --node $NODE
$ openstack baremetal node manage $NODE
$ openstack baremetal node provide $NODE
$ openstack flavor create --ram 131072 --vcpus 16 --disk 480 bm.db
$ openstack flavor set bm.db \
    --property resources:CUSTOM_BAREMETAL_DB=1 \
    --property resources:VCPU=0 --property resources:MEMORY_MB=0 \
    --property resources:DISK_GB=0
\end{lstlisting}
Chaque carte réseau a son port. Le nœud passe par \texttt{verifying} (\texttt{manage}) puis par \texttt{cleaning}
(\texttt{provide}) avant \texttt{available}. La classe \texttt{baremetal-db} devient \texttt{CUSTOM\_\allowbreak BAREMETAL\_\allowbreak DB}.
\end{correction}

\begin{exercice}{Libérer un serveur}\label{ex:ir-liberer}
Un utilisateur supprime son instance bare metal. Quels états le nœud traverse-t-il avant d'être proposé de nouveau, et
pourquoi ne l'est-il pas immédiatement ?
\end{exercice}
\begin{correction}
\texttt{active}, puis \texttt{deleting} (Ironic défait la configuration ajoutée au déploiement), puis \texttt{cleaning} et
\texttt{clean wait} (l'agent efface les disques), enfin \texttt{available}. Le nœud n'est pas rendu aussitôt car le locataire
suivant recevra le même disque : sans nettoyage, il pourrait lire les données du précédent. L'effacement peut durer des
heures.
\end{correction}

\begin{exercice}{Un serveur introuvable}\label{ex:ir-clean}
Un utilisateur obtient « No valid host was found » pour le flavor \texttt{bm.db}, alors qu'un serveur de classe
\texttt{baremetal-db} existe. \texttt{node list} le montre en \texttt{clean failed}, avec \texttt{maintenance} à \texttt{True}.
Pourquoi Nova ne le propose-t-il pas ? Comment le remettre en service ?
\end{exercice}
\begin{correction}
Seuls les nœuds \texttt{available}, hors maintenance et sans instance sont candidats ; un nœud en \texttt{clean failed} n'est
ni l'un ni l'autre. On lit \texttt{last\_error}, on corrige la cause (disque défectueux, BMC), puis :
\begin{lstlisting}
$ openstack baremetal node manage $NODE
$ openstack baremetal node maintenance unset $NODE
$ openstack baremetal node provide $NODE
\end{lstlisting}
Le nettoyage repart du début ; une fois le nœud \texttt{available}, Nova le voit à sa prochaine synchronisation.
\end{correction}

\subsection{Récapitulatif du chapitre}\label{sec:ir-recap}
% ---------------------------------------------------------------------

\begin{aretenir}
\begin{itemize}
  \item Ironic provisionne des serveurs \gls{baremetal} ; avec Nova, un serveur physique se commande comme une machine virtuelle.
  \item Un nœud a un type de matériel (\texttt{ipmi}, \texttt{redfish}), des ports (cartes réseau) et une classe de ressources
        que le flavor réclame (\texttt{resources:CUSTOM\_\dots=1}).
  \item L'API (6385) transmet au conductor par RPC ; le conductor pilote le BMC et le démarrage réseau ; l'agent IPA, dans un
        ramdisk, écrit l'image.
  \item Un nœud passe par \texttt{enroll}, \texttt{manageable}, \texttt{available}, \texttt{active} ; seules les requêtes de
        l'API font quitter un état stable.
  \item Le nettoyage efface les disques entre deux locataires ; un échec laisse le nœud en \texttt{clean failed} et en
        maintenance, d'où l'on sort par \texttt{manage}.
  \item Les réseaux de provisionnement et de nettoyage sont réservés à Ironic ; l'interface \texttt{neutron} isole les
        locataires en reprogrammant les commutateurs.
\end{itemize}
\end{aretenir}
