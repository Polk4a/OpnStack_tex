\section{Nova : le service de calcul}\label{chap:nova}
% =====================================================================

Une fois l'utilisateur authentifié par Keystone (chapitre~\ref{chap:keystone}), la première chose qu'il demande à un cloud est
une machine virtuelle : c'est le travail de Nova, qui ouvre la partie consacrée au socle IaaS. Nova crée et gère les machines
virtuelles d'OpenStack. Ce chapitre situe Nova parmi les autres services, présente ses concepts (instance, gabarit, nœud de
calcul) et ses composants, puis suit la création d'une instance, de la requête au démarrage de la machine. Il explique ensuite
le choix de l'hôte par l'ordonnanceur, le cycle de vie d'une instance et la mise en œuvre. Placement, qui tient l'inventaire des
ressources, a son propre chapitre (chapitre~\ref{chap:placement}).

% ---------------------------------------------------------------------
\subsection{Rôle et place de Nova}\label{sec:nova-role}
% ---------------------------------------------------------------------

\begin{definition}{Nova}
Nova est le service de calcul d'OpenStack (projet \emph{Compute}). Il gère le cycle de vie complet des
\glspl{instance} : création, arrêt, redimensionnement, migration, suppression. Il ne fait pas tourner les
machines lui-même : il pilote un \gls{hyperviseur} (KVM/QEMU le plus souvent) installé sur chaque
\gls{noeudcalcul}.
\end{definition}

\begin{itemize}
  \item \textbf{Problème.} Créer à la demande des machines virtuelles de la bonne taille, sur un serveur qui
        a assez de ressources, sans que l'utilisateur sache où elles tournent.
  \item \textbf{Communique avec.} Keystone (authentification), Placement (inventaire et choix de l'hôte),
        Glance (image), Neutron (réseau), Cinder (volumes), et l'hyperviseur par \gls{libvirt}.
  \item \textbf{Exemple.} \texttt{openstack server create --flavor m1.small --image ubuntu --network private
        vm1} : cette commande appelle l'API REST de Nova, qui crée l'instance \texttt{vm1}.
\end{itemize}

La figure~\ref{fig:nova-env} montre les services avec lesquels Nova échange. Nova valide d'abord le
token auprès de Keystone, demande à Placement où placer l'instance, puis son composant \texttt{nova-compute}
récupère l'image, le réseau et les volumes avant de démarrer la machine.

Un \gls{flavor} comporte un nom, un nombre de vCPU, une taille de mémoire, un disque racine, et des
options : disque éphémère (perdu à la suppression de l'instance), swap, visibilité publique ou limitée à des
projets. Un disque racine de taille \texttt{0} prend la taille native de l'image \parencite{nova-flavors}.
Des propriétés supplémentaires (\emph{extra specs}) affinent la demande. Celles qui commencent par
\texttt{resources:} et \texttt{trait:} sont traduites en requête vers Placement (chapitre~\ref{chap:placement}) ;
d'autres, comme \texttt{hw:cpu\_policy}, s'adressent à l'hyperviseur.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ openstack flavor create --vcpus 2 --ram 4096 --disk 20 m1.custom
$ openstack flavor set m1.custom --property trait:HW_CPU_X86_AVX2=required
$ openstack flavor show m1.custom
\end{lstlisting}
\end{minipage}\par

L'API de Nova est versionnée par \glspl{microversion} : la version de base est \texttt{v2.1} (d'où l'endpoint
\texttt{http://controller:8774/v2.1}), et chaque fonctionnalité ajoutée a son numéro, que le client demande
(option \texttt{--os-compute-api-version}).

\paragraph{Cellules (cells v2).} Pour passer à l'échelle, Nova répartit les nœuds de calcul en
\glspl{cellule}. Chaque cellule a sa propre base de données et sa propre file de messages ; le niveau API,
unique, conserve dans la base \texttt{nova\_api} la correspondance entre chaque instance et sa cellule
(figure~\ref{fig:nova-cells}). La cellule \texttt{cell0} est une base spéciale, sans nœud de calcul, qui garde les
instances que l'ordonnanceur n'a pas pu placer. Tout déploiement comporte au moins une cellule
\parencite{nova-cells}.

Sur le nœud de calcul, \texttt{nova-compute} enchaîne trois demandes avant de lancer la machine : l'image chez
Glance (qu'il télécharge ou référence), un port réseau chez Neutron (créé et lié à l'hôte), et le cas échéant
l'attachement des volumes Cinder. Il appelle ensuite \gls{libvirt}, qui démarre le guest. Si la construction échoue
sur ce nœud, le conductor essaie un hôte de repli, puis l'instance passe à l'état \texttt{ERROR}.

\subsection{Ordonnancement : choisir l'hôte}\label{sec:nova-ordonnancement}
% ---------------------------------------------------------------------

L'\gls{ordonnanceur} travaille en deux temps, résumés par la figure~\ref{fig:nova-sched}. Placement renvoie
d'abord les hôtes qui ont assez de ressources pour la demande ; l'ordonnanceur applique ensuite ses
\emph{filtres} (accepter ou rejeter chaque hôte) puis ses \emph{pondérateurs} (noter ceux qui restent),
retient le mieux classé et réserve ses ressources dans Placement \parencite{nova-scheduling-ref}.

Plusieurs mécanismes orientent le choix. Les \emph{indices d'ordonnancement} (\texttt{--hint}) permettent de
demander \texttt{different\_host}, \texttt{same\_host} ou l'appartenance à un groupe de serveurs. Un
\gls{zonedispo} demandée à la création est traduite en agrégat Placement. L'option
\texttt{[filter\_scheduler] host\_subset\_size} fait tirer au hasard l'hôte final parmi les mieux classés, pour
éviter que des demandes simultanées visent le même.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ openstack server group create --policy anti-affinity web
$ openstack server create --flavor m1.small --image ubuntu --network private \
      --hint group=GROUP_UUID web1
\end{lstlisting}
\end{minipage}\par

% ---------------------------------------------------------------------
\subsection{Mise en œuvre}\label{sec:nova-deploiement}
% ---------------------------------------------------------------------

L'installation se fait en deux temps \parencite{nova-install-controller,nova-install-compute}. Sur le contrôleur,
on crée trois bases (\texttt{nova\_api}, \texttt{nova}, \texttt{nova\_cell0}), l'utilisateur et le service
\texttt{compute} dans Keystone (endpoints sur le port 8774) et l'on installe \texttt{nova-api}, \texttt{nova-conductor},
\texttt{nova-novncproxy} et \texttt{nova-scheduler}. Le fichier \texttt{/etc/nova/nova.conf} renseigne les bases,
le bus de messages, Keystone, Glance et Placement. On initialise ensuite les cellules :

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
# nova-manage api_db sync
# nova-manage cell_v2 map_cell0
# nova-manage cell_v2 create_cell --name=cell1 --verbose
# nova-manage db sync
# nova-manage cell_v2 list_cells
\end{lstlisting}
\end{minipage}\par

Sur chaque nœud de calcul, on installe \texttt{nova-compute} et l'on choisit l'hyperviseur. La commande
\texttt{egrep -c '(vmx|svm)' /proc/cpuinfo} indique si le processeur offre l'accélération matérielle : si le
résultat est \texttt{0}, on utilise \texttt{virt\_type = qemu} au lieu de \texttt{kvm}.

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
# /etc/nova/nova.conf (nœud de calcul, extrait)
[DEFAULT]
transport_url = rabbit://openstack:RABBIT_PASS@controller
my_ip = 10.0.0.31
[vnc]
enabled = true
server_listen = 0.0.0.0
server_proxyclient_address = $my_ip
novncproxy_base_url = http://controller:6080/vnc_auto.html
[libvirt]
virt_type = kvm
\end{lstlisting}
\end{minipage}\par

Le nœud est ensuite déclaré dans la cellule : il faut le « découvrir », à la main ou périodiquement
(\texttt{[scheduler] discover\_hosts\_in\_cells\_interval = 300}).

\par\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=terminal]
$ openstack compute service list --service nova-compute
# nova-manage cell_v2 discover_hosts --verbose
$ openstack hypervisor list
\end{lstlisting}
\end{minipage}\par

\subsection{Exercices corrigés}\label{sec:nova-exercices}
% ---------------------------------------------------------------------

\begin{exercice}{Qui fait quoi ?}\label{ex:nova-roles}
Pour chacune des actions suivantes, nommer le composant de Nova (ou le service) qui en est responsable :
(a)~renvoyer \texttt{202 Accepted} ; (b)~noter les hôtes restants ; (c)~démarrer le guest ; (d)~écrire dans la base de
la cellule pour le compte d'un nœud de calcul ; (e)~lister les hôtes qui ont assez de mémoire.
\end{exercice}
\begin{correction}
(a)~\texttt{nova-api}. (b)~\texttt{nova-scheduler}, par ses pondérateurs. (c)~\texttt{nova-compute}, par libvirt et
l'hyperviseur. (d)~\texttt{nova-conductor} : les nœuds de calcul n'accèdent pas à la base. (e)~Placement,
interrogé par l'ordonnanceur (section~\ref{sec:nova-ordonnancement}).
\end{correction}

\begin{exercice}{Choisir l'hôte}\label{ex:nova-hote}
Une instance demande 4~Go de mémoire, avec un groupe de serveurs en anti-affinité. Cinq hôtes sont candidats :
\texttt{A} (désactivé, 40~Go libres), \texttt{B} (8~Go libres), \texttt{C} (32~Go libres, déjà un membre du groupe),
\texttt{D} (16~Go libres), \texttt{E} (2~Go libres). L'ordonnanceur utilise \texttt{ComputeFilter},
\texttt{ServerGroupAntiAffinityFilter} et \texttt{RAMWeigher}, avec \texttt{host\_subset\_size = 1}. Quel hôte est retenu ?
\end{exercice}
\begin{correction}
\texttt{E} n'a pas assez de mémoire : Placement l'écarte. \texttt{A} est rejeté par \texttt{ComputeFilter} (hôte
désactivé), \texttt{C} par l'anti-affinité (il héberge déjà un membre du groupe). Restent \texttt{B} (8~Go) et \texttt{D}
(16~Go) : \texttt{RAMWeigher} favorise la mémoire libre, donc \texttt{D} est retenu, puis sa réservation est faite
dans Placement.
\end{correction}

\begin{exercice}{Diagnostiquer}\label{ex:nova-diag}
Donner la cause probable et la commande de vérification : (a)~un nœud de calcul tout neuf apparaît \texttt{up} dans
\texttt{openstack compute service list} mais ne reçoit jamais d'instance ; (b)~une création échoue avec
\texttt{No valid host was found} alors que les hôtes sont peu chargés, pour un gabarit qui exige
\texttt{trait:HW\_CPU\_X86\_AVX2=required}.
\end{exercice}
\begin{correction}
(a)~L'hôte n'est pas découvert dans la cellule : \texttt{nova-manage cell\_v2 discover\_hosts --verbose}, ou activer
\texttt{discover\_hosts\_in\_cells\_interval}. (b)~Aucun fournisseur n'expose le trait demandé : on le vérifie avec
\texttt{openstack allocation candidate list --resource VCPU=1 --required HW\_CPU\_X86\_AVX2}, qui renvoie alors une liste
vide (chapitre~\ref{chap:placement}).
\end{correction}

\subsection{Récapitulatif du chapitre}\label{sec:nova-recap}
% ---------------------------------------------------------------------

\begin{aretenir}
\begin{itemize}
  \item Nova gère le cycle de vie des instances mais ne les exécute pas : il pilote l'hyperviseur (KVM/QEMU) par
        libvirt, sur chaque nœud de calcul.
  \item Un gabarit fixe la taille de l'instance ; ses propriétés \texttt{resources:} et \texttt{trait:} deviennent une
        requête vers Placement.
  \item \texttt{nova-api} accepte la requête, \texttt{nova-scheduler} choisit l'hôte, \texttt{nova-conductor}
        coordonne, \texttt{nova-compute} agit sur l'hyperviseur ; tous échangent par le bus de messages.
  \item Les nœuds de calcul n'accèdent pas à la base : ils passent par le conductor. Les cellules répartissent
        bases et files ; \texttt{cell0} garde les échecs de placement.
  \item L'ordonnancement enchaîne Placement (ressources), filtres (accepter ou rejeter), pondérateurs (noter) et
        réservation ; un échec de réservation ou de construction fait essayer un hôte de repli.
  \item La création est asynchrone : l'API répond \texttt{202}, l'instance reste \texttt{BUILD} puis devient
        \texttt{ACTIVE} ou \texttt{ERROR}.
  \item Un nouveau nœud de calcul doit être découvert dans sa cellule avant de recevoir des instances.
\end{itemize}
\end{aretenir}
